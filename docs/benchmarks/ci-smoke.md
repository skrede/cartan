# The continuous-integration smoke subset

**This subset publishes no numbers.** Nothing continuous integration produces from the benchmark
suite is a result: the runner is a shared, contended virtual machine with an unknown neighbour, it
provides neither peer solver, and every figure it computes is discarded when the job ends. Machine
output found in a repository is reasonably read as a measurement unless it says otherwise, so this
file says otherwise.

## What the smoke job covers

- **The suite builds at all.** No other workflow in this repository compiles the benchmark tree, so
  the study's hard dependencies — the description reader, the kinematics library the study programs
  link against, and the revision-pinned robot descriptions the joint bounds come from — are
  otherwise unguarded. The build job fails if any of the four study programs is missing after the
  build, because a suite that skipped every target exits zero and looks exactly like one that built.
- **The capture completes over every stratum.** One robot per periodic rule, plus the seven-axis
  arm so the study's other joint count is exercised, and at most twenty-five targets per stratum.
  Wide enough that a stratum generator that stopped producing targets is caught; small enough that
  the job stays a smoke test.
- **The solvers that ran are the ones the job expects.** The workflow names the participant set it
  expects to be declared and the set it expects to resolve on a runner that provides neither peer
  library, and it fails if either differs. It also fails unless every declared participant that did
  not run appears in the capture's own absence list with a reason. A job that quietly ran one solver
  and went green would be a green check over an empty comparison.
- **The analysis script rebuilds a table from the records just written.** Both record tiers are
  read and the script's own cross-check refuses if they disagree on any published figure. This is
  the claim a reader is offered — the records plus one standard-library-only script — exercised
  against records produced seconds earlier.

## What it deliberately does not cover

- **Any comparison of speed.** No check in the workflow reads an elapsed time, and none compares
  two solvers by one. A solver bounded by a wall-clock cap and a solver bounded by a count of
  kernel evaluations are not commensurable to begin with, and on a contended shared runner a
  wall-clock figure describes the runner.
- **The peer solvers.** Neither is installed on the runner, by choice: a machine without them is
  the ordinary case this study is built to record rather than a broken one, and the job checks that
  their absence is written down instead of being read off a narrower table. Their behaviour is
  measured on a machine that provides them, and what that machine was is recorded beside the
  published records.
- **Accuracy, success rates and any published figure.** The capture is far too small for an order
  statistic to mean anything, and the job neither keeps nor compares one.
- **The calibration search and the timed pass.** Both are built here and neither is run.

## Where the published records live

Beside the report, under `docs/benchmarks/`, together with the environment record of the machine
that produced them. Nothing under this directory is generated by continuous integration.
